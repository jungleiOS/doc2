# Agent如何完成用户超长超详细的任务?

这个问题我自己也被卡过，所以没打算装懂——前段时间我专门去翻了几个主流 Agent 的实现逻辑和相关论文，想把"为什么会翻车"这件事彻底搞明白。下面是我理顺之后的完整逻辑链，不讲架构黑话，只讲因果。

**先说结论：超长任务翻车的根子，不是模型"记性不好"，而是 Agent 从头到尾不知道自己做完了没有。**

---

## 一、先把"为什么会翻车"拆成三件事

一份 6000 到 10000 字的需求，细到"第 3 页表格包含哪些字段、同比怎么算、图表用什么颜色"，让 Agent 一口气读完、记住、一步步做完，公认的难点有三个：

1. **上下文窗口有限。** 现在主流模型普遍是 128K 到 200K token 的窗口，但任务跑起来之后，窗口里装的不只是你的需求，还有中间结果、工具调用记录、报错日志。需求本身占 8K-15K token 不多，可怕的是它会和执行过程"抢位置"。

2. **模型没有持久记忆。** 大模型本质是无状态的，每一轮推理都是一次"瞬时快照"。它"记得"前文，只是因为前文被重新塞进了输入里。一旦某段内容因为窗口不够被挤出去，那段要求就等于从来没说过。

3. **错误会传播。** 中间某一步把字段名理解偏了、漏了一个筛选条件，后面所有输出都会顺着这个错误走下去，而且很难定位错在哪一步。

这三件事在前排答案里基本都被讲透了。但我顺着往下追了一层，发现了真正让我后背发凉的第四件事。

---

## 二、关键问题：Agent 怎么判断"我该停了"？

我原来的直觉是：Agent 干完活会回头核对一遍需求清单，确认都完成了才停。

翻完实现逻辑之后发现，**根本不是。**

以 OpenAI Codex CLI 为例（源码和多方技术拆解一致），它的主循环判断"这轮还继续吗"，看的是一个非常朴素的信号：**模型这一轮有没有发出工具调用**。

- 模型调了工具 → 继续循环；
- 模型只回了一段文字、没调工具 → 本轮结束，输出最终答复。

也就是说，**停止条件和"你的需求有没有被满足"是完全脱钩的。** 系统提示词里写再多"请坚持完成所有要求"，循环也不会去读那句话来决定停不停。

这就解释了无数人遇到过的那个经典现象：让 Agent 改 7 处，它改完 3 处就停下来汇报"已完成 1、2、3 的修改，是否需要我继续？"——它不是偷懒，是它的停止信号里压根没有"7 处都改完"这个概念。

还有一个更隐蔽的坑。上下文快满的时候，Codex 这类工具的做法不是直接报错，而是把历史对话**压缩成一段摘要**再接着跑。摘要是有取舍的，被压缩掉的往往正是这类内容：只在开头说过一次的长篇约束。有技术博客把这叫"governance decay"——规则不是因为失效了而消失，而是因为"太老了"而被摘要略过。

把你的 6000 字需求代进去想一下：任务后半段，你最初那份详细指令在上下文里很可能只剩摘要里的两三句话。**"第 3 页表头必须包含 X"这种只出现一次的要求，正是最容易被压缩掉的。**

---

## 三、这件事有硬数据撑着

这不是经验之谈。AI 评测机构 METR 在 2025 年 3 月发了一篇论文《Measuring AI Ability to Complete Long Tasks》（arXiv: 2503.14499），专门测这件事。

他们给大量真实任务标上"人类专家完成需要多久"，然后让各家 Agent 去跑，得出一个核心结论：

- 人类专家 **4 分钟**能搞定的任务，模型成功率接近 **100%**；
- 人类要花 **4 小时以上**的任务，成功率掉到 **10% 以下**。

中间是一个陡得吓人的落差。

这正好对应题主的场景：一份三四十页报告加工逻辑的需求，人类分析师自己做可能要一整天——这落在了成功率不到 10% 的区间里。**指望换一个上下文更长的模型来解决问题，方向就错了，因为瓶颈根本不在上下文长度，而在"任务一长，系统就失去完成度的判断能力"。**

---

## 四、顺着逻辑往下推：正确姿势是"验收驱动"

把上面三件事串起来，答案就自然浮出水面了：

既然 Agent 自己不知道该做什么、不知道做没做完、还会忘记最初的要求——那就**别把这些事交给它，把它变成一个只需要"对着清单干活"的执行者。**

具体到一份超长需求，我会这样接：

**第一步：把需求翻译成一份可勾选的验收清单。** 把 6000 字文档里的每一句要求，改写成一条一条可以判定"过了/没过"的检查项。比如"第 3 页表格包含类目、均值、同比三列"就是一条合格检查项，"报告要专业"不是。

**第二步：把状态放到对话外面。** 完成一项就落盘记录（完成了哪项、产物文件在哪、失败原因是什么），不依赖模型"记得刚才算过什么"。上下文被压缩、窗口重开、甚至进程重启，都不影响接着干。

**第三步：每一步做完立刻独立核验。** 表格行数对不对、空值率多少、同比公式是不是按需求写的——用脚本或工具去验，而不是让模型自己宣布"这步完成了"。它自己的总结不算证据。

**第四步：收尾时对着清单过一遍，而不是听它汇报。** 清单上 30 项全勾了，任务才算完；它说"我觉得都做完了"一文不值。

---

## 五、回到这个问题本身

题主问"这种情况下该如何让 Agent 遵循用户指令一步步完成全部分析"。

顺着上面的逻辑，我的回答是：**先接受一个事实——现在的 Agent 没有能力"记住并遵守"一份 6000 字的指令，这不是提示词工程能解决的。**

然后换个思路：那份需求文档不要直接喂给 Agent 当指令，而是先由人或程序把它加工成两样东西——一张带依赖关系的任务步骤表，和一份逐项可判定的验收清单。Agent 只负责按步骤执行，完成度的判断由清单接管。

说白了：

> **超长任务的核心不是让 Agent 记住更多，而是让它需要记住的东西变少。把"记住需求"从模型的脑子里，搬到文件系统里。**

这也是我看下来所有靠谱方案的公约数——不管是任务图、执行轨迹、还是多 Agent 分工，本质都在做同一件事：把模型记不住、判不了的东西，外置成结构。差别只在于外置得多漂亮。
