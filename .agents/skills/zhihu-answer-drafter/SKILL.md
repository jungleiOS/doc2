# 知乎回答起草助手（zhihu-answer-drafter）

把确认要答的知乎问题写成回答初稿。选题侧流程（怎么选题、打分、好物适配评估）在 **zhihu-question-scout** skill；本 skill 只管「题定了之后怎么写」。

## 工作流程

### 1. 浏览器通道检查（必做）

读问题描述和填编辑器都要操作用户真实浏览器。优先用 **ego-browser**：

```bash
ego-browser nodejs <<'EOF'
const ts = await useOrCreateTaskSpace('zhihu-draft');   // 按名字幂等获取，不用记 id
const tab = await openOrReuseTab('https://www.zhihu.com/', {wait:true});
await new Promise(r=>setTimeout(r,3000));
const out = await js(`document.title`);
console.log(out);
EOF
```

注意：ESM 环境（`import fs from 'fs'` 可用，不能 require）；工作目录不是仓库根目录，读写文件用绝对路径；`js()` 里的模板字符串在 heredoc 中会被外层再解析一层，避免在 js 代码字符串里嵌套 `\n` 字面量。用户接管过浏览器后命令会报 hard stop，等用户说继续后 `claimTaskSpace(id)` 恢复。

备用通道 **WebBridge**（浏览器无窗口时会报 `No current window`，此时直接换 ego-browser）：`~/.kimi-webbridge/bin/kimi-webbridge status`，要求 `running: true` 且 `extension_connected: true`，否则按 kimi-webbridge skill 的 `references/operations.md` 处理；session 名 `zhihu-draft`。

### 2. 先读问题完整描述再动笔（必做）

用户确认题目后（或直接指定题目后），**直接起草，不重新选题、不再二次确认**。先逐个 navigate 到问题 URL，sleep 3 秒后用下面的 evaluate 脚本提取标题 + 补充说明（问题描述里常有具体机型、使用场景、提问者的真实困惑，回答必须逐点回应，只看标题写稿等于瞎写）：

```js
(()=>{const t=(document.querySelector(".QuestionHeader-title")||{}).innerText||"";const d=(document.querySelector(".QuestionRichText")||document.querySelector("div.RichText.ztext")||{}).innerText||"";return JSON.stringify({t:t.trim(),d:d.trim().slice(0,2000)})})()
```

描述默认折叠，拿到的 `d` 以「…显示全部」结尾时**必须点开展开再读一次**（不展开 = 没读完整描述，起草作废）。展开按钮的选择器是 `button.QuestionRichText-more`（2026-09-12 实测：用「找 innerText 恰为『显示全部』的叶子元素」的定位法找不到该按钮，别用）。

**读完后把描述原文逐字留在起草上下文里，成稿后做「逐点回应检查」**：提问者说的每一句困惑，稿子里必须有明确对应段落，且开头不许替提问者认领立场——「你的直觉」「你观察到的」「你觉得」这类读心句一律禁写，只能引用其原话或说「很多人」（2026-09-28 实战教训：不送充电头篇开头替提问者认领「你的直觉」，被用户当场揪出；提问者原话只有「一直很疑惑，最疑惑的是苹果这样，很多厂家跟进」）。

**术语门槛自查（2026-10-07 实战教训：蜂窝故障篇初稿把 AT&T、基带、C2、X80、毫米波直接砸进结论句，用户要求给吃瓜群众解释）**：电信公司、芯片、协议、监管术语这类圈内名词，**第一次出现时给一句式大白话注释**（如「AT&T 是美国三大运营商之一，地位大概相当于中国的移动」「基带就是手机里负责连移动网络的那颗芯片」），括号带过、不堆在开头、不教科书腔；苹果用户常识范围内的词（Face ID、iOS 版本号）不注。判断标准：一个只带着问题来搜答案的吃瓜群众，读完第一句结论能不能跟上。

### 3. 成稿规则

- 调用 `zhihu-viral-answer` skill 的流程和结构。
- **一次只打磨一篇（迭代改稿流）**：用户确认题目后先起草这一篇，用户提改写意见 → 就地改 → 用户认可并发布后，才讨论下一篇。不一次批量出多篇。
- 素材优先复用归集目录里的主文和已有回答，保持一致的口吻和「文尾引流」固定写法，但**篇章结构必须逐篇差异化**（2026-08-31 复盘：8 天 12 篇统一「先说结论 + 实测案例 + 引流」骨架，疑似被算法判批量生产遭降权）——开头钩子、展开顺序、详略分布每篇换一种组织方式，不允许多篇套同一模板。
- **事实核查**：涉及具体设备型号、充电功率、协议规格时，先用 WebSearch 核实（官网规格页、充电头网及小白测评/科技美学/钟文泽/极客湾等大科技媒体实测优先），不要沿用未经核实的数字；用户提供的真实设备信息要融入回答。**正文引用实测数据时，给信源挂上原文链接**（如充电头网评测页）。**表述范围不得超过核实范围**——只核实到 X90 Pro 的代工厂信息，稿子里就写「X90 Pro 那颗」，不要外推成全系列（2026-08-21 实战教训）。**核查软件/服务类事实时，必须额外核查「国区可用性」**——海外官方口径不等于国区可用（2026-09-12 实战：Adobe 官方标注 Photoshop iPad 版国区不可用；Apple 智能国行设备不可用，均有官方支持页实锤），软件订阅价格也要查中国区定价而非美元区。
- **事实核查与配图采集可派子代理并行执行**（主代理专注成稿）：事实核查子代理按「事实表述｜信源｜URL」编号清单返回、末尾单列「未核实/有争议」项；配图采集子代理按「文件｜画面内容｜来源｜页面URL｜原图URL」清单返回并自行 ReadMediaFile 校验。子代理结论进稿前主代理抽查关键数字与成品图。

### 4. 配图工作流（强制：每篇 ≥4 张配图；用户无实拍条件，不要向用户索图）

**每篇草稿必须配不少于 4 张图，主体为真实图片（媒体实拍/测评图、官方图），每张都必须与所在段落内容直接相关。AI 生成图仅限两类破例：流程图/决策图/思维导图等示意类图；以及内含媒体实拍/测评图的合成图（如案例拼图）。除此之外的 AI 生成图严禁充当配图**。

起草时先想清楚需要哪些图（产品外观、铭牌、接口、实测数据、对比表格、示意图等），然后**从可信大科技媒体的图文评测里检索实拍/测评图并引用其数据**。

- **可信信源池**：充电头网（充电/功率类首选）、小白测评、科技美学、钟文泽、极客湾（Geekerwan）。这些媒体的实拍图和实测数据都可引用——正文挂原文链接，图片挂图源注（如「图源：小白测评」）。
- **检索路径**：WebSearch 搜「机型/产品名 + 评测 + 媒体名」锁定图文评测页 → FetchURL 拿原文、用 `curl` 抓 HTML 按正文段落定位目标图的 `src`；
- 站点下载经验（2026-09-12 实测）：Notebookcheck 的 `fileadmin/...` 原图被 Cloudflare 拦（403），但其 `_processed_/webp/...` 处理图可直抓；GSMArena 整站拦 curl，未采用；IT之家（img.ithome.com）、快科技（img1.mydrivers.com）直链可抓；苹果官网产品页图直链可抓；被拦的图可经 Kimi 图片代理（kimi-web-img.kimi.ai）中转。下载时带 `Referer: <信源域名>` 头（static.chongdiantou.com 有 Referer 防盗链，裸 curl 会 403），存到归集目录 `cover-assets/raw/<事件名>/`；
- **必须 ReadMediaFile 回看校验图片内容**——段落与图片的对应关系不一定符合直觉（实测踩过坑：按段落顺序推定的「铭牌照」实为线材照），内容不符就换相邻图片重新校验；
- 插入草稿用相对路径 + 图源注（知乎编辑器不支持外链图，填编辑器时由作答辅助协议把本地图片通过知乎「导入图片」插进去，见 [references/publish-assist.md](references/publish-assist.md)）。

**破例类图的制作与缺口补足**：示意类图（流程图/决策图/思维导图）用归集目录既有的「HTML 渲染 → Puppeteer 截图」工作流制作；含媒体实拍的合成图在 `cover-assets/` 里拼版后截图。两类图产出后同样**必须 ReadMediaFile 回看校验**。媒体检索后真实图不足 4 张时，用破例类图补足到 4 张再交付，不向用户索要实拍。

**外链图替换（图床流程，2026-09-12 起）**：配图完成后，运行 `node .agents/skills/image-host-upload/upload.js <草稿路径>` 将本地图上传到临时图床，**直接在草稿中把本地图片路径替换为图床 URL**，不额外生成 `-hosted.md` 副本。项目根 `.image-host-cache.json` 永久保留「本地路径 → URL」映射供过期后溯源重传。替换后在草稿文尾追加**图片溯源映射块**（HTML 注释包裹，逐条「本地路径 -> 图床URL」+ `--force` 重传命令，标注「发布前删除本段」）——裂图后凭映射直接找回本地原图重传，不用再翻缓存 JSON。贴入编辑器后**必须确认图片实际显示正常**（平台转存成功）才放任图床过期；裂图则回退到作答辅助协议的本地图片导入流程。

### 5. 去 AI 味（应对平台 AI 检测）

初稿完成后，用 `khazix-writer` skill 的风格内核做一遍「活人感」改写——口语化转场替代小标题和 bullet、长短句断裂（一句话独立成段）、禁用冒号/破折号/双引号、疑问句做节奏刹车。保留知乎侧骨架：信息密度、关键句加粗、引流固定写法、无谢邀。注意只借风格内核，**不套公众号固定尾部**，固定引流链接的标题一字不动。

结构过关后还要过一遍**句级 AI 腔检查**（2026-09-24 贴膜篇实战教训：段落结构已是活人感，单句仍被读者揪出 AI 味）。逐句朗读，命中以下特征就重写：

- **三连排比短句**：「不摔、不碎、不花」这类为气势而生造的三字/四字并排，正常人说话不会这么均衡——只保留一个意思、一个修饰。
- **同字重复修辞**：「抗摔，抗摔，还是抗摔」——AI 特有的强调句式，改成「翻来覆去讲的都是抗摔」这类自然表述。
- **硬凑对仗**：「要硬才不刮，要韧才不碎」——为了格式对称牺牲语序自然，改成「想抗刮就得做硬，想耐摔就得做韧」。
- **为凑排比牺牲搭配**：「装进裤兜、揣进沙滩、塞进包里」——「揣进沙滩」动宾不合常理。排比里的每一项必须单独成立，念不通就拆成正常句式。
- **修辞修饰先行**：「完美的划痕实验」「完美的解决方案」——「完美」是 AI 高频空修饰词，换成有信息量的限定（如「货真价实的划痕测试」）或直接删掉。
- **书面化设问转场**：「翻译成日常语言是什么？」「这意味着什么？」——这类提问式过渡是模板痕迹，直接陈述结论。
- **「不是A，而是B」转折句式**：「不是某个人的性格，而是四次选择」「不是X，而是Y」——AI 高频论证模板，一篇里出现两次以上就是明显腔。改成直接陈述（「真正的原因是四次选择」）或换成因果、让步等自然句式。注意区分：「这不是因为…而是因为…」这类讲事实因果的口语句不算（2026-09-25 软硬一体篇实战教训：全稿 4 处被读者逐一揪出）。
- **假精确的条件状语**：「前提是它每次选这条路的时候，都恰好赌对了」——为凑书面感硬加的逻辑条件，还常带事实错误（苹果这条路根本没有「每次」）。写之前先问自己这个条件在现实中成立吗，不成立就删。
- **不解释的行业黑话**：「被认定是『守门人』」——监管术语、圈内缩写直接砸进正文，普通读者看不懂。要么用大白话说清是谁要干什么（「iOS 被列进欧盟重点监管名单」），要么干脆删掉。
- **强行金句式收束**：「护城河的水从哪儿来的答案：不是墙高，是里面住着舒服」「从牢不可破变成贵到难破」——为制造记忆点硬凹的对仗比喻，读者第一反应是「这什么鬼」。结尾用平常话把意思说完即可，金句让事实自己长出来。
- **事实写超前**：「国行 AI 晚了一年多才逐步落地」——实际只完成备案、功能一根毛没上。写进度类事实必须核实到「现在进行到哪一步」，宁可写「还没上线」也不写「逐步落地」（2026-09-26 iOS 护城河篇实战教训）。
- **立场预设**：「你的直觉大方向没错」「你观察到的破发是真的」——没等提问者表态就替对方认领立场，是读心。开头只能引用提问者原话或写「很多人」，立场让提问者自己认（2026-09-28 实战教训：这类错生成时自我感觉通顺，几乎无法自查，必须靠逐点回应检查兜底）。
- **生造词**：「跟进账」「同行账」这类为凑平行结构硬拼的复合词——动词或关系名词直接贴在「账」前面，中文里不存在这种搭配，念出来就不通。比喻能自然延伸就延伸（环保账、经济账，环保/经济本身就是名词概念），延伸到某个标签念不通时，别硬造词，直接把那段换成一句大白话标题（2026-09-28 实战教训，同上几乎无法自查）。

判断标准：把句子读出来，凡是为凑格式、凑气势而生的搭配和排比，都改成正常人说这件事的顺序。信息可以密度高，句子的骨头必须是口语的。

### 5.5 立场句标注与作者仲裁（2026-10-07 起）

初稿交付前，把全文每个段落的**立场/判断句**（下结论、给归因、做站队的那一句）用 `<!-- 判断句 -->` HTML 注释紧邻标注，并在交付汇报里单列一张「判断句清单」（原文 + 行号）。注释保留在稿中，供作者审稿时逐条仲裁：

- 作者审稿动作是**指错式仲裁**：对每条判断句说「认/不认 + 一句理由」。理由写多烂都算数，但不许只给「感觉不对」三个字——指错必须给出理由，理由是作者观点能力增长的抓手。
- 作者不认的判断句：agent 必须改，且改动不得波及其他判断句。
- 立场对不对的最终仲裁权在作者，不在 agent。agent 负责把立场写清楚、标出来，不负责替作者决定信什么。

背景：2026-10-04 蜂窝故障篇首次启用此约定，作者对 8 条判断句中的 1 条提出异议（术语门槛问题），按条修改后即定稿。此约定同时是「作者指错能力」的训练器——作者的认知增长发生在被迫把「感觉不对」翻译成一句理由的时刻。

### 6. GEO/SEO 审查（去 AI 味之后）

调用 `zhihu-geo-optimizer` skill 做一遍机器可读性审查——关键词布局、开头结论前置、信源入句、实体全称、结尾可引用结论句。只做增量改写；若与活人感冲突，活人感优先（仲裁规则见该 skill）。

### 7. 存档与登记

初稿存到对应话题归集目录的**问题文件夹**下（如 `多口充电器选购指南/充电线老是坏/zhihu-充电线老是坏-v1.md`），问题文件夹不存在则新建（文件夹名 = 问题核心关键词），配图也散放在同一文件夹内；**先读该话题目录的 AGENTS.md 并遵守其约定**（如引流主文的固定链接写法、排版约定）。起草同时在话题根目录的 `问题对应表.md` 追加一行（日期/草稿文件/问题链接/描述摘要/状态）。

### 8. 作答辅助协议

「判 AI 创作应对协议」和「用 ego-browser 把草稿填进知乎编辑器（含图片导入）」两节在 [references/publish-assist.md](references/publish-assist.md)，起草、改稿、填编辑器时必读。

### 9. 收尾

全部草稿交付后关闭浏览器会话，按本次实际使用的通道二选一：

- **ego-browser（主力）**：`completeTaskSpace('zhihu-draft', { keep: false })`，必须放在独立最后一个 heredoc 里执行，且只在前序输出确认任务真正完成后才调用（细节见 ego-browser skill）。
- **WebBridge（备用）**：

```bash
curl -s -X POST http://127.0.0.1:10086/command -d '{"action":"close_session","args":{},"session":"zhihu-draft"}'
```

## 禁忌

- 不替用户实际提交/发布任何回答，绝不点发布按钮。
- 禁止只看问题标题就起草；未读问题完整描述写出的稿子必须作废重写。
- 起草不编造第一手体验；用户未提供的设备/经历不写进回答，涉及参数先核查再落笔。
- 配图红线：草稿配图不足 4 张不得交付；真实图（媒体实拍/测评图、官方图）必须 ReadMediaFile 回看核实过且与内容相关；AI 生成图仅限流程图/决策图/思维导图等示意类、或内含媒体实拍/测评图的合成图，其余 AI 图严禁使用；不向用户索要实拍图。
- 去 AI 味只借 khazix-writer 风格内核，不套公众号固定尾部；固定引流链接的标题一字不动。
