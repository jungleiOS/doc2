# 知乎选题助手（zhihu-question-scout）

从用户的知乎邀请回答 + 创作中心推荐问题中，基于「需求 × 机会 × 供给」三因子模型（见第 5 步），每次选出 **3 个** 期望收益最高的问题，确认后起草回答。

## 工作流程

### 1. WebBridge 健康检查（必做）

```bash
~/.kimi-webbridge/bin/kimi-webbridge status
```

要求 `running: true` 且 `extension_connected: true`，否则按 kimi-webbridge skill 的 `references/operations.md` 处理。后续所有请求用 session 名 `zhihu-scout`。

### 2. 建立用户选题画像

仓库文章按「归集目录」组织（如 `多口充电器选购指南/` 内含主文、衍生回答、子级 `drafts/`）。快速扫描以下位置提炼用户擅长领域、已有观点和已答主题：

- 根目录的 `*.md`
- 各文章归集目录（含其子级 `drafts/`）
- `drafts/`、`published/`（如有）

只读标题和各级 `#`/`##` 标题，不要全文通读。画像要点：核心领域（如充电/数码/AI 硬件）、已覆盖主题（避免重复）、可复用的实测案例。

### 3. 抓取问题列表

知乎创作中心「问题推荐」页有两个标签（已实测可直接抓取）：

- 邀请回答：`https://www.zhihu.com/creator/featured-question/invited`
- 推荐问题：`https://www.zhihu.com/creator/featured-question/recommend`

对每个页面：navigate → sleep 3~4 秒 → 用下面的 evaluate 脚本提取（已实测可用）：

```js
(()=>{const qs=[...document.querySelectorAll("a[href*=\"/question/\"]")].map(a=>({t:(a.innerText||"").trim().replace(/\n+/g," ").slice(0,80),h:a.getAttribute("href")})).filter(x=>x.t.length>5&&/\/question\/\d+$/.test(x.h||""));const seen=new Set();const out=[];for(const x of qs){if(!seen.has(x.h)){seen.add(x.h);out.push(x);}}return JSON.stringify(out)})()
```

注意：

- 通过 curl 调用 WebBridge 时，JS 需做 JSON 转义。
- 返回空数组时先 `snapshot` 确认是否登录墙（是则提示用户先在浏览器登录知乎）。
- 两个来源合并后按问题 ID（URL 中的数字）去重；邀请的问题优先级高于推荐。

### 4. 历史去重

读取 `outlines/选题历史.md`，提取所有问题 ID，从候选列表中剔除——**选过的和标注「已弃选」的都不再推荐**。文件不存在则视为无历史。

### 5. 选题模型：需求 × 机会 × 供给

**第一性原理推导**：一篇回答的期望收益 = 触达流量 × 赢下前排的概率 − 写作成本。映射到三个可测量因子：

- **D 需求（流量池）**：关注人数决定长尾推荐，浏览量决定存量曝光，近期活跃度决定是否仍在流量上升期。
- **O 机会（竞争格局）**：回答数少、头部回答赞数低 = 前排空缺，同等质量更容易冒头。
- **M 供给（我方胜率）**：领域匹配 + 素材复用度。复用度高意味着质量上限高、且写作成本低——所以成本不单独计分，由 M 隐含。

**总分 = D × O × M（乘法，满分 125）**。用乘法而非加法：任一因子接近零，期望收益就是零，乘法天然体现短板效应。

#### 5.1 硬否决（任一命中即淘汰，不打分）

- 与已发布文章/已有草稿主题完全重复且无新角度
- 用户没有一手经验的边界领域（医疗/法律/金融投资等，遵守根 AGENTS.md）
- 问题已死亡：最近 6 个月无新回答，且不是「xx 怎么选」类经典长尾搜索题
- 读完问题描述后发现题主诉求与标题不符、或实际主题与本仓库领域无关

#### 5.2 两阶段漏斗

- **阶段 A 粗筛（只看标题和来源，不打开问题页）**：凭领域匹配快速排除，保留 ≤8 个进入精评。
- **阶段 B 精评（逐个打开问题页）**：navigate → sleep 3 秒 → 先抓统计数据，再按第 7 步的脚本抓问题描述（同一次访问完成两件事）。

统计抓取脚本（已实测：问题页数据区文本为「关注者\n数字\n被浏览\n数字」，用 `body.innerText` + 正则，对 DOM 改版更鲁棒）：

```js
(()=>{const t=document.body.innerText;const num=re=>{const m=t.match(re);if(!m)return 0;const v=parseFloat(m[1].replace(/,/g,""));return Math.round(v*(/万/.test(m[0])?1e4:1))};return JSON.stringify({follow:num(/关注者\s*([\d.,]+万?)/),view:num(/被浏览\s*([\d.,]+万?)/),answers:num(/([\d.,]+万?)\s*个回答/),topUp:num(/([\d.,]+万?)\s*人赞同了该回答/)})})()
```

抓不到数字时用 `snapshot` 人工读取「关注者 / 被浏览 / x 个回答」三个数；头部回答赞数（`topUp`，取默认排序第一答案的「x 人赞同了该回答」）抓不到就跳过，不打 0 分。

#### 5.3 打分细则（各 1-5 分）

**D 需求**（按抓到的数据对档，近 30 天有新回答 +1，封顶 5）：

| 分 | 关注人数 | 或浏览量 |
|----|----------|----------|
| 5 | ≥1万 | ≥1000万 |
| 4 | ≥1000 | ≥100万 |
| 3 | ≥100 | ≥10万 |
| 2 | ≥10 | ≥1万 |
| 1 | 以上皆不满足 | 以上皆不满足 |

**O 机会**（头部回答赞数以默认排序第一的答案为准）：

| 分 | 条件 |
|----|------|
| 5 | 回答数 <20 且无 500 赞以上回答（前排空缺） |
| 4 | 回答数 <50 且头部回答 <1000 赞 |
| 3 | 回答数 50-200 |
| 2 | 回答数 200-1000 |
| 1 | 回答数 >1000，或头部回答 ≥1万赞 |

**M 供给**：

| 分 | 条件 |
|----|------|
| 5 | 主文/已有草稿直接覆盖，可整段复用实测与观点，且能自然引流主文 |
| 4 | 核心观点已有，需补 1-2 个新论据 |
| 3 | 领域内，但需较多新调研 |
| 2 | 擦边领域 |
| 1 | 基本无积累 |

**排序规则**：总分取前 3；并列时邀请 > 推荐，再并列比浏览量。

#### 5.4 校准回路（科学方法的闭环）

选题历史表记录打分时的「关注/浏览/回答数」快照（见第 8 步）。回答发布约 7 天后，回采自己回答的赞数和问题下排名，在历史表追加「复盘」行。用实际表现检验打分模型：发现系统性偏差（如高分题持续没流量）就调整分档阈值或维度定义。闭环即：**测量 → 假设 → 验证 → 迭代**。

### 6. 输出选题单

```markdown
## 本次选题（共 N 个候选，粗筛 M 个，精评后选出 3 个）

### 1. [问题标题](问题URL)
- 来源：邀请 / 推荐
- 数据快照：关注 x / 浏览 x / 回答数 x
- 评分：D=? O=? M=? → 总分 ?（满分 125）
- 匹配理由：……（必须引用具体的已有文章文件名）
- 建议切入角度：……（指明可复用哪篇文章的哪些观点）
- 注意：……（如有事实核查点或风险）
```

然后询问用户：要对哪些题目起草回答？

### 7. 起草回答（用户确认后）

用户确认题目后（或直接指定题目后），**直接起草，不重新选题、不再二次确认**。规则：

- **先读问题完整描述再动笔（必做）**：用 WebBridge 逐个 navigate 到问题 URL，sleep 3 秒后用下面的 evaluate 脚本提取标题 + 补充说明（问题描述里常有具体机型、使用场景、提问者的真实困惑，回答必须逐点回应，只看标题写稿等于瞎写）：

```js
(()=>{const t=(document.querySelector(".QuestionHeader-title")||{}).innerText||"";const d=(document.querySelector(".QuestionRichText")||document.querySelector("div.RichText.ztext")||{}).innerText||"";return JSON.stringify({t:t.trim(),d:d.trim().slice(0,2000)})})()
```

- 调用 `zhihu-viral-answer` skill 的流程和结构。
- **一次只打磨一篇（迭代改稿流）**：用户确认题目后先起草这一篇，用户提改写意见 → 就地改 → 用户认可并发布后，才讨论下一篇。不一次批量出多篇。
- 素材优先复用归集目录里的主文和已有回答，保持一致的口吻和「先说结论 + 实测案例 + 文尾引流」结构。
- **事实核查**：涉及具体设备型号、充电功率、协议规格时，先用 WebSearch 核实（官网规格页、充电头网实测优先），不要沿用未经核实的数字；用户提供的真实设备信息要融入回答。**正文引用实测数据时，给信源挂上原文链接**（如充电头网评测页）。**表述范围不得超过核实范围**——只核实到 X90 Pro 的代工厂信息，稿子里就写「X90 Pro 那颗」，不要外推成全系列（2026-08-21 实战教训）。
- **配图工作流**（引用信源实测图时）：
  1. FetchURL 拿到信源原文后，用 `curl` 抓原文 HTML，按正文段落定位目标图的 `src`；
  2. 下载时带 `Referer: <信源域名>` 头（static.chongdiantou.com 有 Referer 防盗链，裸 curl 会 403），存到归集目录 `cover-assets/raw/<事件名>/`；
  3. **必须 ReadMediaFile 回看校验图片内容**——段落与图片的对应关系不一定符合直觉（实测踩过坑：按段落顺序推定的「铭牌照」实为线材照），内容不符就换相邻图片重新校验；
  4. 插入草稿用相对路径 + 图源注，并提醒用户发布时需本地上传（知乎编辑器不支持外链图）。
- **去 AI 味（应对平台 AI 检测）**：初稿完成后，用 `khazix-writer` skill 的风格内核做一遍「活人感」改写——口语化转场替代小标题和 bullet、长短句断裂（一句话独立成段）、禁用冒号/破折号/双引号、疑问句做节奏刹车。保留知乎侧骨架：信息密度、关键句加粗、引流固定写法、无谢邀。注意只借风格内核，**不套公众号固定尾部**，固定引流链接的标题一字不动。
- 初稿存到对应归集目录的 `drafts/`，命名 `zhihu-<主题>-v1.md`；**先读该目录的 AGENTS.md 并遵守其约定**（如引流主文的固定链接写法、排版约定）。起草同时在 `drafts/问题对应表.md` 追加一行（日期/草稿文件/问题链接/描述摘要/状态）。
- 用户明确排除的题目：不起草，把问题 ID 记入 `outlines/选题历史.md` 并在标题后标注「（已弃选，不再推荐）」。浏览中遇到的**与已答主题近重复的题**也顺手记入历史（标注「近重复已答主题」），避免下轮重复推荐。

#### 7.1 平台判 AI 创作（限流/制裁）的应对协议

实战记录：2026-08-19 有 3 篇按结构模板直出的回答被判 AI 创作限流，全部废弃，按「去 AI 味」风格重写后才通过。

- **触发特征（复盘推断）**：规整小标题 + 密集 bullet、段落等长、八股连接词（首先/其次/最后）、通篇无口语破绽。结构模板只是思考骨架，成稿必须过「去 AI 味」改写，这是必做项不是可选项。
- **被制裁后**：先向用户要平台通知原文，对照通知调整风格策略，不盲目重写；同主题旧稿直接废弃换角度重写，不在原稿上小修小补；在 `outlines/选题历史.md` 和草稿目录的 AGENTS.md 里标注「已废弃：被判 AI 创作」。
- **发布节奏**：刚被制裁过的高风险期，一次只发一篇，用户确认一篇没被接着制裁再继续下一篇（本轮实测策略：第一篇过了才写第二篇，第二篇过了观察后再写第三篇）。

### 8. 记录与收尾

把本次选出的问题追加到 `outlines/选题历史.md`（含打分时的数据快照，供 5.4 校准回路回采）：

```markdown
| 日期 | 问题ID | 标题 | 来源 | 关注 | 浏览 | 回答数 |
|------|--------|------|------|------|------|--------|
| 2026-08-18 | 1961371990993663235 | 华为手机+联想笔记本，求推荐一个能共用的100W充电器？ | 邀请 | 152 | 3.1万 | 8 |
```

旧记录保持原列不动，新行追加数据列；发布 7 天后回采时，在同一问题下方追加一行，来源列写「复盘」，标题列写自己回答的赞数与问题下排名。

然后关闭浏览器会话：

```bash
curl -s -X POST http://127.0.0.1:10086/command -d '{"action":"close_session","args":{},"session":"zhihu-scout"}'
```

## 禁忌

- 不替用户实际提交/发布任何回答，只做选题和起草。
- 不编造问题数据；抓取失败就如实说明，不假装看到了列表。
- 打分必须有抓到的数据支撑（D/O 按快照对档，M 按已有文件对档），禁止凭感觉拍分；数据抓不到就如实标注并降级处理。
- 选题理由必须引用具体的已有文章文件名，禁止空泛的「和你的领域匹配」。
- 起草不编造第一手体验；用户未提供的设备/经历不写进回答，涉及参数先核查再落笔。
- 禁止只看问题标题就起草；未读问题完整描述写出的稿子必须作废重写。
