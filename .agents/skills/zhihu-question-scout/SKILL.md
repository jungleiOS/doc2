# 知乎选题助手（zhihu-question-scout）

从用户的知乎邀请回答 + 创作中心推荐问题中，基于「需求 × 机会 × 供给」三因子模型（见第 5 步），每次选出 **3 个** 期望收益最高的问题，确认后起草回答。

## 工作流程

### 1. 浏览器通道检查（必做）

优先用 **ego-browser**（2026-08-22 起实测为主力通道，用户真实浏览器、登录态在）：

```bash
ego-browser nodejs <<'EOF'
const ts = await useOrCreateTaskSpace('zhihu-scout');   // 按名字幂等获取，不用记 id
const tab = await openOrReuseTab('https://www.zhihu.com/creator/featured-question/invited', {wait:true});
await new Promise(r=>setTimeout(r,3000));
const out = await js(`document.title`);
console.log(out);
EOF
```

注意：ESM 环境（`import fs from 'fs'` 可用，不能 require）；工作目录不是仓库根目录，读写文件用绝对路径；`js()` 里的模板字符串在 heredoc 中会被外层再解析一层，避免在 js 代码字符串里嵌套 `\n` 字面量。用户接管过浏览器后命令会报 hard stop，等用户说继续后 `claimTaskSpace(id)` 恢复。

备用通道 **WebBridge**（浏览器无窗口时会报 `No current window`，此时直接换 ego-browser）：

```bash
~/.kimi-webbridge/bin/kimi-webbridge status
```

要求 `running: true` 且 `extension_connected: true`，否则按 kimi-webbridge skill 的 `references/operations.md` 处理。后续所有请求用 session 名 `zhihu-scout`。

### 2. 建立用户选题画像

仓库文章按「归集目录」组织（如 `多口充电器选购指南/` 内含主文、衍生回答、子级 `drafts/`）。快速扫描以下位置提炼用户擅长领域、已有观点和已答主题：

- 根目录的 `*.md`
- 各文章归集目录（含其子级 `drafts/`）
- `drafts/`、`published/`（如有）

只读标题和各级 `#`/`##` 标题，不要全文通读。画像要点：核心领域（如充电/数码/AI 硬件）、已覆盖主题（避免重复）、可复用的实测案例。

另需加载**粉丝画像**（`analytics/` 下有最新数据报告时读取其粉丝画像节），选题角度优先锚定粉丝已有兴趣点。当前画像（2026-08-31 复盘）：25 岁以下占 60.5%、涨粉主力为 iPad/教育优惠类苹果生态内容、数码 3C 未进兴趣 TOP15——泛 3C 选题（如「充电宝电芯哪种好」）对粉丝没有推送基础，应改造为苹果生态 + 学生场景角度（如「教育优惠买的 iPad 配什么充电宝」「MacBook 宿舍一个充电器搞定全部设备」）；角度改造不了的泛 3C 题在「建议切入角度」里如实说明风险，由用户定夺。

### 3. 抓取问题列表

知乎创作中心「问题推荐」页有两个标签（已实测可直接抓取）：

- 邀请回答：`https://www.zhihu.com/creator/featured-question/invited`
- 推荐问题：`https://www.zhihu.com/creator/featured-question/recommend`

对每个页面：navigate → sleep 3~4 秒 → **先滚动加载到 40 条**再提取。

滚动加载（2026-08-28 起，候选量从 20 增至 40）：列表是无限滚动加载，用下面的脚本滚动到目标条数或到底（滚动由页面自身触发，不额外刷新页面，风控成本与手刷一致）：

```js
(async()=>{const q=()=>[...document.querySelectorAll("a[href*=\"/question/\"]")].filter(a=>/\/question\/\d+$/.test(a.getAttribute("href")||"")).length;let last=0;for(let i=0;i<10;i++){window.scrollTo(0,document.body.scrollHeight);await new Promise(r=>setTimeout(r,1500));const n=q();if(n>=40||n===last)break;last=n;}return q()})()
```

然后用下面的 evaluate 脚本提取（已实测可用）：

```js
(()=>{const qs=[...document.querySelectorAll("a[href*=\"/question/\"]")].map(a=>({t:(a.innerText||"").trim().replace(/\n+/g," ").slice(0,80),h:a.getAttribute("href")})).filter(x=>x.t.length>5&&/\/question\/\d+$/.test(x.h||""));const seen=new Set();const out=[];for(const x of qs){if(!seen.has(x.h)){seen.add(x.h);out.push(x);}}return JSON.stringify(out)})()
```

注意：

- 通过 curl 调用 WebBridge 时，JS 需做 JSON 转义。
- 返回空数组时先 `snapshot` 确认是否登录墙（是则提示用户先在浏览器登录知乎）。
- 两个来源合并后按问题 ID（URL 中的数字）去重；邀请的问题优先级高于推荐。
- **主动搜新问题（第三来源，2026-08-31 起）**：邀请/推荐列表里大多是衰退期老问题。两个列表粗筛后存活 <5 个时，用知乎搜索领域关键词（如「充电宝」「充电器」）按时间排序，或看「数码」话题的实时流，打捞**诞生期/爆发期问题**——提出 ≤7 天、已有 3-8 个回答、关注者 >20 且在增长。新问题在 24h 内有热榜/推荐爆发窗口，是冷启动红利区；等问题进入死寂期再答，等于在废墟里捡流量。

### 4. 历史去重

读取 `outlines/选题历史.md`，提取所有问题 ID，从候选列表中剔除——**同一问题 ID 选过的和标注「已弃选」的都不再推荐**。文件不存在则视为无历史。

注意（2026-08-28 起）：去重只在**问题 ID 层面**做。**主题级近重复不再剔除**——撞已答主题或内容部分重叠的题仍可进入精评和最终选题单，但必须按 5.6 的规则注明。

### 5. 选题模型：需求 × 机会 × 供给

**第一性原理推导**：一篇回答的期望收益 = 触达流量 × 赢下前排的概率 − 写作成本。映射到三个可测量因子：

- **D 需求（流量池）**：关注人数决定长尾推荐，浏览量决定存量曝光，近期活跃度决定是否仍在流量上升期。
- **O 机会（竞争格局）**：回答数少、头部回答赞数低 = 前排空缺，同等质量更容易冒头。
- **M 供给（我方胜率）**：领域匹配 + 素材复用度。复用度高意味着质量上限高、且写作成本低——所以成本不单独计分，由 M 隐含。

**总分 = D × O × M（乘法，满分 125）**。用乘法而非加法：任一因子接近零，期望收益就是零，乘法天然体现短板效应。

#### 5.1 硬否决（任一命中即淘汰，不打分）

- 用户没有一手经验的边界领域（医疗/法律/金融投资等，遵守根 AGENTS.md）
- **超出用户本人知识储备、用户无法为内容站台的题**（2026-08-23 实战教训：「5V USB 口测出 90 多伏」涉及 Y 电容/安规等电路底层知识，稿写完了用户才说自己不懂、不敢发，整篇作废。选题时不能只看仓库素材覆盖度，还要看用户本人是否懂这个细分领域；拿不准就在选题单里标注知识门槛，让用户先确认）
- **死问题：关注者 <20，直接否决**（2026-08-31 全量复盘：关注者 <10 的 6 篇带货回答，含 3 篇排名第 1，总阅读仅 53、篇均 <9——问题从未进过流量池，排第 1 也没流量。「没人回答」往往意味着「没人搜」，不是前排空缺）
- 问题已死亡或流量枯竭：最近 6 个月无新回答，且不是「xx 怎么选」类经典长尾搜索题。**累计浏览量只代表历史，不代表当下日活**——浏览 >1 万但回答数 <10 且近 30 天无新回答的题，是流量高峰已过的「遗迹」（复盘实证：10.8 万浏览的「快充协议」题仅 6 个回答，排第 4 阅读只有 8；若有流量早有几十人来答），同样否决
- 读完问题描述后发现题主诉求与标题不符、或实际主题与本仓库领域无关

#### 5.2 两阶段漏斗

- **阶段 A 粗筛（只看标题和来源，不打开问题页）**：凭领域匹配快速排除，保留 ≤8 个进入精评。近重复主题不排除，带上撞题标注进入精评（见 5.6）。
- **阶段 B 精评（逐个打开问题页）**：navigate → sleep 3 秒 → 先抓统计数据，再按第 7 步的脚本抓问题描述（同一次访问完成两件事）。

统计抓取脚本（已实测：问题页数据区文本为「关注者\n数字\n被浏览\n数字」，用 `body.innerText` + 正则，对 DOM 改版更鲁棒；topUps 为 2026-08-29 新增，按 DOM 顺序取默认排序前 5 条回答的赞数，回答卡片选择器如失效需实测校准）：

```js
(()=>{const t=document.body.innerText;const num=re=>{const m=t.match(re);if(!m)return 0;const v=parseFloat(m[1].replace(/,/g,""));return Math.round(v*(/万/.test(m[0])?1e4:1))};const ups=[...document.querySelectorAll(".ContentItem.AnswerItem, .List-item")].map(el=>{const m=(el.innerText||"").match(/([\d.,]+万?)\s*人赞同了该回答/);if(!m)return null;const v=parseFloat(m[1].replace(/,/g,""));return Math.round(v*(/万/.test(m[0])?1e4:1))}).filter(v=>v!==null);return JSON.stringify({follow:num(/关注者\s*([\d.,]+万?)/),view:num(/被浏览\s*([\d.,]+万?)/),answers:num(/([\d.,]+万?)\s*个回答/),topUps:ups.slice(0,5)})})()
```

抓不到数字时用 `snapshot` 人工读取「关注者 / 被浏览 / x 个回答」三个数；`topUps`（默认排序前 5 条回答的赞数）抓不到就人工读前 5 条的赞数，都不打 0 分。

阶段 B 另需记录**问题生命周期信号**（2026-08-31 起）：问题创建时间（问题日志可见）和最近一条新回答的日期（问题页切「按时间排序」看首条）。这两个值是 5.1 枯竭判定和 5.3 D 加分的依据，写入选题单数据快照和第 8 步历史表。

#### 5.3 打分细则（各 1-5 分）

**D 需求**（按抓到的数据对档。注意表中浏览量是**累计值**，只证历史不证当下，必须结合 5.2 的生命周期信号使用；近 30 天有新回答 +1，诞生期/爆发期问题——提出 ≤7 天且关注者 >20 且回答数 3-8——再 +1，封顶 5）：

| 分 | 关注人数 | 或浏览量 |
|----|----------|----------|
| 5 | ≥1万 | ≥1000万 |
| 4 | ≥1000 | ≥100万 |
| 3 | ≥100 | ≥10万 |
| 2 | ≥10 | ≥1万 |
| 1 | 以上皆不满足 | 以上皆不满足 |

**O 机会（夺前排难度，2026-08-29 起改为 K=5 门槛制）**：门槛赞数 T = 默认排序第 5 名回答的赞数（即 topUps 第 5 个值；回答不足 5 条时 T=0）：

| 分 | 条件 |
|----|------|
| 5 | T ≤ 5（第 5 名个位数赞，或不满 5 条回答） |
| 4 | T ≤ 50 |
| 3 | T ≤ 500 |
| 2 | T ≤ 2000 |
| 1 | T > 2000 |

修正项：

- **垄断但后排空虚不降档**：top1 赞数很高但 T 很低（如第 1 名 2000 赞、第 5 名 20 赞），说明问题有流量但前排后半段好打，按 T 值正常打分，不因头部赞数高降档。
- **能力对照（先验，随 5.4 复盘更新）**：账号 500–5000 粉，基础赞数能力先验 5–20 赞。T ≤ 50 是主战场；T ≤ 500 需内容质量明显超出现有前排才选；T > 500 默认不选，除非 D=5 且 M=5。

**M 供给**（先用 Grep 以问题关键词检索各归集目录和 `drafts/`，命中哪些文件决定档位，不凭印象）：

| 分 | 条件 |
|----|------|
| 5 | 主文/已有草稿直接覆盖，可整段复用实测与观点，且能自然引流主文 |
| 4 | 核心观点已有，需补 1-2 个新论据 |
| 3 | 领域内，但需较多新调研 |
| 2 | 擦边领域 |
| 1 | 基本无积累 |

**排序规则**：总分取前 3；并列时邀请 > 推荐，再并列比近期活跃度（最近新答日期更近者优先，不比累计浏览量）。

#### 5.4 校准回路（科学方法的闭环）

选题历史表记录打分时的「关注/浏览/回答数/T/最近新答」快照（见第 8 步）。回答发布后回采两个时点：**24 小时赞数**（检验冷启动测试曝光给不给量）和 **7 天赞数 + 当时排名**（稳态结果），在历史表追加「复盘」行。回采调用 **zhihu-answer-tracker** skill 完成（创作中心批量采五指标 + 问题页抓排名 + 回写复盘行）。

复盘数据维护两个量：

- **能力先验**（我方回答能拿到的赞数区间）：初始值 5–20 赞（2026-08-29，依据 500–5000 粉账号 + 3 条复盘样本 1/6/1 赞），攒到约 10 条复盘后按实际分布更新，并同步修订 5.3 的「能力对照」；
- **分档阈值**：若实际排名系统性优于/差于 O 档预期（如 T ≤ 50 也持续打不进前 5），调整 5.3 的 T 分档。

**2026-08-31 全量复盘结论**（12 篇带货回答 + 账号级数据，详表见 `analytics/带货数据采集-2026-08-31.md`）：

- 死问题实证：关注者 <10 的 6 篇（含 3 篇排名第 1）总阅读仅 53 → 已固化为 5.1「关注者 <20 硬否决」。
- 枯竭遗迹实证：10.8 万 / 3.1 万 / 1.1 万累计浏览的三题，排名 4/4/9，阅读仅 8/19/20 → 累计浏览量不再作为当下流量依据，只看近期活跃度（5.1、5.2、5.3）。
- 带货隔离：近 7 天账号总阅读 6,682，12 篇带货回答合计仅 166（占 2.5%），非带货内容流量正常 → 账号无全局限流，但「商品卡商业降权 + 0 互动冷启动失败」双重降权成立 → 第 7 步默认延迟插卡。
- 粉丝错配：25 岁以下 60.5%、兴趣 TOP15 无数码、涨粉主力为 iPad/教育优惠内容 → 选题角度锚定规则（第 2 步）。
- 频率与模板红线：8 天 12 篇带货回答（1.5 篇/天）+ 统一「先说结论」模板，疑似触发营销号检测 → 第 7 步发布频率与结构差异化约束。
- 文章定位：两篇专栏主稿阅读 240/34，远低于回答流量来源 → 专栏文章不进问题流量池，只作背书与引流终点，流量主战场是回答；不为文章本身投入流量预期。

闭环即：**测量 → 假设 → 验证 → 迭代**。

#### 5.5 好物适配评估（阶段 B 顺带完成）

阶段 B 打开问题页时已拿到标题、描述和数据快照，逐题调用 **zhihu-haowu-evaluator** skill，输出三档结论：推荐插 / 可插不优先 / 不插（附一句话理由和商品方向）。

- 好物结论**不进 D×O×M 总分**——好物是变现维度，不是流量维度，混进总分会扰乱选题排序。
- 总分并列时，优先「推荐插」的题。
- 结论写进选题单（第 6 步），起草时作为**选品方向和插卡时机**的依据（第 7 步）。
- **插卡时机默认延迟（2026-08-31 起）**：带商品卡的回答遭商业降权，叠加 0 互动冷启动失败直接沉底。默认策略为**首发不带卡、纯干货抢前排，发布 48h 后若排名进前 5 或赞数达到能力先验区间，再编辑插入商品卡**。仅当问题本身是强购买意图（题主明码求购，如「预算 200 求推荐充电宝」）且好物评估为「推荐插」时，才允许首发直接插卡。

#### 5.6 重复主题注明机制（2026-08-28 起）

主题撞题不再淘汰，但**入选时必须特别注明**，让用户知情决策：

- **完全重复**：与已发布/已有草稿主题相同 → 选题单里标注「⚠ 重复主题：与《xxx》撞题」，并写清新的切入角度是什么；想不出新角度才在「注意」里说明风险，由用户决定答不答。
- **部分重叠**：部分内容可复用但问题侧重不同 → 标注「⚠ 部分重叠：与《xxx》重叠在 xxx 部分」，写清本题侧重点是哪里、重叠内容怎么换说法（避免两篇回答文字雷同被平台判重复内容）。
- 注明格式固定在选题单的「注意」字段，前缀 `⚠ 重复主题` / `⚠ 部分重叠`，一眼可辨。
- 近重复题仍记入 `选题历史.md`（标注撞题对象），但不再写「不再推荐」——它的作用是供下轮选题时查撞题、写注明。

### 6. 输出选题单

```markdown
## 本次选题（共 N 个候选，粗筛 K 个，精评后选出 3 个）

### 1. [问题标题](问题URL)
- 来源：邀请 / 推荐
- 数据快照：关注 x / 浏览 x（累计）/ 回答数 x / 创建于 x / 最近新答 x（生命周期信号）
- 评分：D=? O=? M=? → 总分 ?（满分 125）
- 好物评估：推荐插（商品方向）/ 可插不优先 / 不插（一句话理由，按 zhihu-haowu-evaluator 结论）；插卡时机：48h 后延迟插（默认）/ 首发直插（仅强购买意图题）
- 匹配理由：……（必须引用具体的已有文章文件名）
- 建议切入角度：……（指明可复用哪篇文章的哪些观点）
- 注意：……（如有事实核查点或风险；撞题题必须以 `⚠ 重复主题` / `⚠ 部分重叠` 前缀开头，见 5.6）
```

然后询问用户：要对哪些题目起草回答？

### 7. 起草回答（用户确认后）

用户确认题目后（或直接指定题目后），**直接起草，不重新选题、不再二次确认**。规则：

- **先读问题完整描述再动笔（必做）**：用 WebBridge 逐个 navigate 到问题 URL，sleep 3 秒后用下面的 evaluate 脚本提取标题 + 补充说明（问题描述里常有具体机型、使用场景、提问者的真实困惑，回答必须逐点回应，只看标题写稿等于瞎写）：

```js
(()=>{const t=(document.querySelector(".QuestionHeader-title")||{}).innerText||"";const d=(document.querySelector(".QuestionRichText")||document.querySelector("div.RichText.ztext")||{}).innerText||"";return JSON.stringify({t:t.trim(),d:d.trim().slice(0,2000)})})()
```

- 调用 `zhihu-viral-answer` skill 的流程和结构。
- **一次只打磨一篇（迭代改稿流）**：用户确认题目后先起草这一篇，用户提改写意见 → 就地改 → 用户认可并发布后，才讨论下一篇。不一次批量出多篇。
- 素材优先复用归集目录里的主文和已有回答，保持一致的口吻和「文尾引流」固定写法，但**篇章结构必须逐篇差异化**（2026-08-31 复盘：8 天 12 篇统一「先说结论 + 实测案例 + 引流」骨架，疑似被算法判批量生产遭降权）——开头钩子、展开顺序、详略分布每篇换一种组织方式，不允许多篇套同一模板。
- **事实核查**：涉及具体设备型号、充电功率、协议规格时，先用 WebSearch 核实（官网规格页、充电头网及小白测评/科技美学/钟文泽/极客湾等大科技媒体实测优先），不要沿用未经核实的数字；用户提供的真实设备信息要融入回答。**正文引用实测数据时，给信源挂上原文链接**（如充电头网评测页）。**表述范围不得超过核实范围**——只核实到 X90 Pro 的代工厂信息，稿子里就写「X90 Pro 那颗」，不要外推成全系列（2026-08-21 实战教训）。
- **配图工作流（强制：每篇 ≥3 张配图；用户无实拍条件，不要向用户索图）**：**每篇草稿必须配不少于 3 张图，主体为真实图片（媒体实拍/测评图、官方图），每张都必须与所在段落内容直接相关。AI 生成图仅限两类破例：流程图/决策图/思维导图等示意类图；以及内含媒体实拍/测评图的合成图（如案例拼图）。除此之外的 AI 生成图严禁充当配图**。起草时先想清楚需要哪些图（产品外观、铭牌、接口、实测数据、对比表格、示意图等），然后**从可信大科技媒体的图文评测里检索实拍/测评图并引用其数据**。
  - **可信信源池**：充电头网（充电/功率类首选）、小白测评、科技美学、钟文泽、极客湾（Geekerwan）。这些媒体的实拍图和实测数据都可引用——正文挂原文链接，图片挂图源注（如「图源：小白测评」）。
  - **检索路径**：WebSearch 搜「机型/产品名 + 评测 + 媒体名」锁定图文评测页 → FetchURL 拿原文、用 `curl` 抓 HTML 按正文段落定位目标图的 `src`；
  - 下载时带 `Referer: <信源域名>` 头（static.chongdiantou.com 有 Referer 防盗链，裸 curl 会 403），存到归集目录 `cover-assets/raw/<事件名>/`；
  - **必须 ReadMediaFile 回看校验图片内容**——段落与图片的对应关系不一定符合直觉（实测踩过坑：按段落顺序推定的「铭牌照」实为线材照），内容不符就换相邻图片重新校验；
  - 插入草稿用相对路径 + 图源注，并提醒用户发布时需本地上传（知乎编辑器不支持外链图）。
- **破例类图的制作与缺口补足**：示意类图（流程图/决策图/思维导图）用归集目录既有的「HTML 渲染 → Puppeteer 截图」工作流制作；含媒体实拍的合成图在 `cover-assets/` 里拼版后截图。两类图产出后同样**必须 ReadMediaFile 回看校验**。媒体检索后真实图不足 3 张时，用破例类图补足到 3 张再交付，不向用户索要实拍。
- **好物插入（默认延迟插卡，2026-08-31 起）**：带货回答**首发一律不带商品卡**（强购买意图题除外，见 5.5），草稿正文不写卡片占位，只在文尾加一行执行备注：`【延迟插卡：发布 48h 后若排名进前 5 或赞数 ≥ 能力先验下沿，编辑插入——商品：[商品名](京东/淘宝商品链接)，位置建议：xxx】`（链接从归集目录主文或好物决策卡里取，没有就先查好物库补齐），供 48h 复盘回采（zhihu-answer-tracker）时对照执行。强购买意图题首发直插的，沿用占位格式 `【好物卡：[商品名](链接)】`，位置与数量遵循 zhihu-haowu-evaluator 建议。无真实体验的商品一律不插；正文不写返佣/利益声明。
- **发布频率红线（2026-08-31 起）**：带货回答同一自然日最多发 1 篇、每周 ≤3 篇；与上一篇带货回答间隔 <24h 时主动提醒用户缓发（8 天 12 篇的节奏已疑似触发营销号检测）。非带货干货回答不受此限，可作为带货回答之间的节奏缓冲，也是重建账号垂直权重的手段。
- **去 AI 味（应对平台 AI 检测）**：初稿完成后，用 `khazix-writer` skill 的风格内核做一遍「活人感」改写——口语化转场替代小标题和 bullet、长短句断裂（一句话独立成段）、禁用冒号/破折号/双引号、疑问句做节奏刹车。保留知乎侧骨架：信息密度、关键句加粗、引流固定写法、无谢邀。注意只借风格内核，**不套公众号固定尾部**，固定引流链接的标题一字不动。
- **GEO/SEO 审查（去 AI 味之后）**：调用 `zhihu-geo-optimizer` skill 做一遍机器可读性审查——关键词布局、开头结论前置、信源入句、实体全称、结尾可引用结论句。只做增量改写；若与活人感冲突，活人感优先（仲裁规则见该 skill）。
- 初稿存到对应归集目录的 `drafts/`，命名 `zhihu-<主题>-v1.md`；**先读该目录的 AGENTS.md 并遵守其约定**（如引流主文的固定链接写法、排版约定）。起草同时在 `drafts/问题对应表.md` 追加一行（日期/草稿文件/问题链接/描述摘要/状态）。
- 用户明确排除的题目：不起草，把问题 ID 记入 `outlines/选题历史.md` 并在标题后标注「（已弃选，不再推荐）」。浏览中遇到的**与已答主题近重复的题**也顺手记入历史（标注撞题对象，如「近重复：xxx」），供下轮选题写注明用——**不要再标「不再推荐」**，近重复题按 5.6 仍可入选。

## 禁忌

- 不替用户实际提交/发布任何回答，只做选题和起草。
- 禁止推荐关注者 <20 的问题；禁止把累计浏览量当作当下流量依据，D 打分必须结合生命周期信号。
- 禁止给带货回答的草稿首发就插商品卡（强购买意图题除外）；禁止安排同一自然日发布多篇带货回答。
- 不编造问题数据；抓取失败就如实说明，不假装看到了列表。
- 打分必须有抓到的数据支撑（D/O 按快照对档，M 按已有文件对档），禁止凭感觉拍分；数据抓不到就如实标注并降级处理。
- 选题理由必须引用具体的已有文章文件名，禁止空泛的「和你的领域匹配」。
- 起草不编造第一手体验；用户未提供的设备/经历不写进回答，涉及参数先核查再落笔。
- 禁止只看问题标题就起草；未读问题完整描述写出的稿子必须作废重写。
- 配图红线：草稿配图不足 3 张不得交付；真实图（媒体实拍/测评图、官方图）必须 ReadMediaFile 回看核实过且与内容相关；AI 生成图仅限流程图/决策图/思维导图等示意类、或内含媒体实拍/测评图的合成图，其余 AI 图严禁使用；不向用户索要实拍图。
